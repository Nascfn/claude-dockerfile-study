## 1. Headline findings

1. **Lint-level security improved in every case.** All 30 generated Dockerfiles
   scored at or below the original on the weighted static score, and 27 of 30
   scored strictly lower. The mean score fell from 13.3 (human) to 7.4 (Opus
   5.5), 7.3 (Sonnet 5.5) and 6.3 (Haiku 5.5): a mean per-repository reduction
   of 44%, 45% and 53%. Each model's improvement is significant on a paired
   sign test (p ≤ 0.008) even with only 10 repositories.
2. **Every generated Dockerfile builds, without the model ever running a
   build.** All 30 completed every build step on the first attempt. 29 images
   were exported and scanned; one (Haiku, ClimateVision) was too large for the
   build sandbox's disk.
3. **Vulnerability counts in the built image did not improve consistently.**
   Critical+High CVEs went down in 4 repositories and up in 4 for Opus and for
   Sonnet (2 unchanged); for Haiku they went down in 2 and up in 6 (of 9). None
   of these differences is significant.
4. **The CVE result is explained by base-image choice.** Half of the originals
   end on Alpine. The models preferred Debian "slim" images (6, 6 and 9 of 10
   final stages). In all 11 runs where a model replaced an Alpine or distroless
   base with a Debian one, Critical+High CVEs rose (for example 6 → 48, 13 →
   135, 0 → 38). Where the original used a full Debian image, the models cut
   CVEs sharply (2008 → 45 in one repository).
5. **Fewer images run as root.** 7 of 10 original images run as root; 4 do for
   each model (Haiku: 4 of its 9 scanned images). The four that stay root are
   the same for every model, and are
   applications that plausibly need it (a Docker daemon controller, a
   WireGuard manager, a port-83 web server, an entrypoint that drops
   privileges itself).
6. **The three models are close to each other.** No pairwise difference between
   models is significant. Haiku had the lowest static score and the lowest
   cost (USD 0.65 for all 10 repositories against 1.67 for Sonnet and 6.43 for
   Opus), but chose Debian bases most often, so its images carry the most
   CVEs. Sonnet was the fastest (40 s mean); Haiku the slowest (135 s mean).
7. **"Lower lint score" and "more secure" are not the same thing.** In 12 of
   the 29 scanned runs the static score went down while Critical+High CVEs went
   up; both went down in 10. A study that used only Hadolint and Trivy config
   would have concluded that the models always win.

### 2.2 Ranking rule (fixed before any Dockerfile was scanned)

`score = 3·(Hadolint errors) + 2·(Hadolint warnings) + 1·(Hadolint info) + 1·(Hadolint style) + 4·(Trivy CRITICAL) + 3·(Trivy HIGH) + 2·(Trivy MEDIUM) + 1·(Trivy LOW)`

Ties keep discovery order. The same score is used as the "weighted static
score" metric.

### 2.4 What the models could see ("code only")

Rules in `scripts/strip_hints.py`, applied identically to every repository:

1. `.git` is not copied (the history contains the original Dockerfile).
2. Deleted by name: `Dockerfile*`, `*.dockerfile`, `.dockerignore`,
   `docker-compose*.y(a)ml`, `compose*.y(a)ml`, `docker-entrypoint*`,
   `entrypoint*.sh`, `.devcontainer/`, `.github/`, `.gitlab-ci.yml`,
   `.circleci/`, top-level `docker/` and `.docker/`, `k8s/`, `kubernetes/`,
   `helm/`, Helm chart directories, `fly.toml`, `render.yaml`, `heroku.yml`,
   and similar deployment descriptors.
3. In documentation files (`.md`, `.rst`, `.txt`, …) every line that mentions
   Docker, containers, Podman, Kubernetes or Helm is deleted, together with the
   fenced code block it sits in. Documentation files with "docker" in their
   name are deleted.
4. Source code and build files are not edited. The number of remaining
   "docker" mentions in code is recorded per repository (table above).

### 2.5 Generation

- **Runner:** `claude -p` (Claude Code CLI 2.1.326), one fresh process per run,
  started in a private copy of the stripped repository, no session persistence.
- **Models:** `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`,
  `--effort high`. Each transcript confirms the model that answered.
- **Tools offered:** Read, Glob, Grep, Write. No shell, no in-place edit, no
  web, no sub-agents, no MCP servers, no skills. The model cannot build, run or
  test anything.
- **Prompt** (identical for all 30 runs, `scripts/prompt.txt`). It does not
  mention security:

  > This repository does not have a Dockerfile yet. Please write one.
  >
  > Read the code to work out how the project is built and run, then create a
  > file named `Dockerfile` in the repository root that builds and runs the
  > application. If the Dockerfile needs supporting files to work (for example
  > a `.dockerignore` or a startup script), create those too. Do not modify or
  > overwrite any existing file.
  >
  > You cannot run commands in this session, so you will not be able to build
  > or test the image. Work on your own and do not ask me any questions. When
  > you are done, briefly list the files you created.

- **Runs:** one per (repository, model), 30 in total, three in parallel.
- **Audit of all 30 runs** (`results/generated/*/*/run.json`): the pinned model
  answered in every run; no existing file was modified or deleted; no tool call
  touched a path outside the run's workspace. Four runs tried to call a tool
  that was not offered (Bash three times, Edit once); the CLI rejected all
  four. One of the Bash attempts (Haiku) was a `curl` to the npm registry to
  look up a package version.

### 2.6 Evaluation

- **Static:** Hadolint 2.15.1 (`-f json`) and Trivy 0.76.2
  (`trivy config`) on the Dockerfile alone.
- **Build:** `docker build` (Docker Engine 29.10.0, BuildKit), 20-minute limit.
  - *Original:* built in the untouched clone at the pinned commit.
  - *Generated:* built in the untouched clone with the container artifacts
    from rule 2 removed and the model's files added. The documentation edits
    from rule 3 are not applied to the build context (see Challenge 7.3).
- **Image:** `trivy image --scanners vuln,secret`, one vulnerability database
  for every image (updated 2026-11-17 13:00 UTC, `--skip-db-update`). Also
  recorded from `docker image inspect`: configured user, size, healthcheck.
- **Sandbox shim:** the build sandbox intercepts TLS, so each base image named
  in a `FROM` line was wrapped in a thin layer that trusts the sandbox
  certificate and points `apt` at HTTPS. The Dockerfile under test is never
  edited on disk (a temporary copy with rewritten `FROM` lines is passed to
  `docker build -f`), and scanners read the unmodified file. The shim adds
  certificate files and a few environment variables to the image, and no
  packages. It is applied to originals and generated files alike.

## 3. Deviations from the proposal

| Proposal | What was done | Why |
|---|---|---|
| Fable 5.1, Opus 5, Sonnet 5, Haiku 4.5 (4 models, 40 files) | Opus 5.5, Sonnet 5.5, Haiku 5.5 (3 models, 30 files) | Current model versions; Fable dropped by decision |
| "Give Claude Code the repository" | Repository with all container hints stripped; the model may also write supporting files | Makes "from the code alone" defensible |
| Sessions in the Claude Code app | Headless `claude -p` sessions restricted to four file tools | Enforces "cannot run the code" and gives an audit trail |
| Trivy on "what is being built" | Both Trivy config (Dockerfile) and Trivy image (built image) | Separates misconfiguration from inherited vulnerabilities |
| Not in the proposal | Build success as a validity metric; structural feature counts; paired tests | A Dockerfile that does not build is not an improvement |
| "A group of Dockerfiles", pick 10 that score poorly | 545 → 43 → 10 with fixed queries, mechanical filters and a ranking rule fixed in advance | Reproducible selection |

## 4. Metric definitions

| Metric | Definition | Tool | Better is |
|---|---|---|---|
| M1 Hadolint findings | Number of rule violations reported for the Dockerfile, also split by severity (error, warning, info, style) | Hadolint | lower |
| M2 Trivy misconfigurations | Number of failed Dockerfile checks, also split by severity (CRITICAL, HIGH, MEDIUM, LOW) | Trivy config | lower |
| M3 Weighted static score | `3·error + 2·warning + info + style + 4·CRITICAL + 3·HIGH + 2·MEDIUM + LOW` over M1 and M2 | derived | lower |
| M4 Score reduction | `(M3 original − M3 generated) / M3 original`, per repository, then averaged | derived | higher |
| M5 Build success | 1 if every Dockerfile step completes under `docker build` within 20 minutes | Docker | 1 |
| M6 Critical+High CVEs | Vulnerabilities of severity CRITICAL or HIGH in the built image (OS packages and language packages) | Trivy image | lower |
| M7 Fixable Critical+High CVEs | Subset of M6 for which a fixed package version exists | Trivy image | lower |
| M8 Total CVEs | All vulnerabilities in the built image, any severity; also split into OS packages and application dependencies | Trivy image | lower |
| M9 Runs as root | 1 if the image's configured user is empty, `root` or `0` | docker inspect | 0 |
| M10 Image size | Uncompressed image size in MB | docker inspect | lower |
| M11 Rule prevalence | Number of Dockerfiles (of 10) that trigger a given rule at least once | Hadolint, Trivy | lower |
| M12 Generation effort | Wall-clock seconds, turns, tool calls, output tokens and cost reported by the CLI | Claude Code | lower |

M3 is the selection criterion and the primary static outcome. M6 is the
primary image outcome. M5 is a validity gate.

## 6. Observations for the Discussion section

**6.1 The models fix the smells that linters look for.** Use of `latest` fell
from 4 originals to 1, 0 and 0. Consecutive `RUN` instructions (DL3059) fell
from 6 to 1, 0 and 0. "Image user should not be root" (DS-0002) fell from 7 to
4 for every model. Unpinned `apk add` (DL3018) fell from 6 to 2, 3 and 0. All
30 runs wrote a `.dockerignore` (8 originals have one). 28 of 30 generated
files are multi-stage (7 originals).

**6.2 They also introduce a few.** Unpinned `apt-get install` (DL3008) rose
from 4 to 6, 6 and 8, a side effect of moving to Debian bases. Named rather
than numeric users (DL3066) rose from 4 to 6. No model pinned an image by
digest (one original does). "No HEALTHCHECK" (DS-0026) barely moved (6 → 5).

**6.3 Base-image choice dominates the CVE numbers.** Operating-system packages
account for almost all CVEs (T6b against T6c). Trivy lists many unfixed Debian
CVEs that Alpine does not carry, so "slim Debian" loses to Alpine on raw
counts even when it is a reasonable engineering choice. Restricting to CVEs
that have a fix (T5b) narrows the gap but does not remove it (for example
wg-rest-api 13 → 32). Raw CVE counts therefore measure the base image far more
than the quality of the Dockerfile.

**6.4 The models moved away from Alpine without saying why.** None of the 11
Dockerfiles that switched from Alpine or distroless to Debian explains the
choice in a comment. A plausible reading (an interpretation, not something the
data shows) is that Debian slim is a compatibility-first default: prebuilt
wheels and native modules assume glibc, so it is the safer bet for a model that
cannot test its build. It is the main place where the human authors did better
on a measured outcome.

**6.5 Staying root was a decision, not an oversight.** All three models kept
root for the same four applications. Haiku wrote the reason into the Dockerfile
each time: Wings "needs the Docker socket", wg-rest-api "must create and
configure the wg0 interface", webchat2api binds port 83. A linter still counts
these as findings, which is part of why wings and wg-rest-api show little or
no score improvement. For Mediarium all three models wrote an entrypoint that
starts as root and then drops privileges, as the original does.

**6.6 Reading the code versus pattern-matching.** pelican/wings checks
`/etc/os-release` for `ID="distroless"` in two Go files. Opus was the only
model to notice: it reproduced the original's unusual step that writes that
file and kept a distroless base, which is why its score equals the original's
(11) while Sonnet and Haiku, which missed it, score 6. The lower-scoring
Dockerfiles here are probably the less correct ones. This check does not
measure whether the application behaves correctly, only whether it builds.

**6.7 Size.** Median image size fell from 617 MB to 293, 262 and 334 MB. The
exception is ClimateVision. The original installs CPU-only PyTorch and says
why in a comment; Opus did the same (4.7 GB image). Sonnet and Haiku installed
the default wheels, which bundle GPU libraries: Sonnet's image is 12.2 GB
against 6.9 GB for the original, and Haiku's could not be exported at all.

**6.8 Cheap model, similar result.** Haiku matched or beat both larger models
on the static score in 9 of 10 repositories at about a tenth of Opus's cost. It
also took the most turns and wrote about three times as many output tokens as
Opus at the same effort setting.

**6.9 Tool restriction mattered.** Four of 30 sessions tried to use a tool that
had been withheld. With a shell available, at least some runs would have looked
things up or tested the build, which is a different experiment.

## 7. Challenges faced

1. **Sandbox network.** The build environment intercepts TLS, allows HTTPS only
   through a proxy, and blocks plain HTTP and most github.com downloads. Fixed
   with the base-image shim (2.6), host networking and proxy build arguments.
   Three selection candidates were lost to it (2.3).
2. **Docker Hub rate limiting.** Anonymous pulls returned HTTP 429. Fixed by
   configuring `mirror.gcr.io` as a registry mirror.
3. **Stripping broke a build.** The first evaluation built generated
   Dockerfiles inside the stripped copy. All three Mediarium builds failed
   because the project compiles its own documentation at build time and a
   heading had been removed as a "Docker hint". The build context was changed
   to the original source tree plus the model's files; all three then built.
   Those first results were discarded.
4. **Stripping rules were too broad.** A rule deleting any directory named
   `charts` removed a front-end source folder, and a rule deleting any
   directory named `docker` removed a Go package in pelican/wings. Both were
   narrowed before any model saw the affected repositories. The second fix
   came after the first four repositories had been generated; re-stripping
   confirmed that it changed nothing in those four.
5. **Disk.** The sandbox allows about 25 GB of working space. Images are
   deleted right after scanning and caches pruned under a lock. The Haiku
   ClimateVision image still could not be exported (two attempts).
6. **Daemon lifetime.** The Docker daemon was stopped by the session's 2-hour
   limit mid-evaluation; three builds were recorded as failures for that
   reason, deleted, and rerun after the daemon was restarted.
7. **Old runtimes.** A Java 8 repository and two GPU-image repositories passed
   the first filter and were removed from the pool before ranking, by adding
   rules to the filter rather than by hand.

## 8. Limitations and threats to validity

- **One run per model per repository.** Model output is not deterministic, so
  differences between models (and single-repository differences) cannot be
  separated from run-to-run noise.
- **Ten repositories, chosen for being bad.** Selecting the worst-scoring
  originals guarantees room to improve and some regression to the mean. The
  result says "the models improve poor Dockerfiles", not "the models beat
  human authors in general".
- **The score rewards short, conventional files.** It is a sum of findings, so
  longer Dockerfiles score worse, and it weights style issues alongside real
  risks. The selected originals are mostly careful, long, multi-stage files
  rather than naive ones.
- **Lint findings and CVE counts are proxies.** Neither measures
  exploitability. Unfixed Debian CVEs inflate M6 and M8; a root user that the
  application needs still counts under M2 and M9.
- **Build success is not runtime correctness.** No container was started. A
  generated image may build and still fail at start-up (6.6 is a likely case).
- **Hint removal is incomplete.** Source code that talks about Docker was left
  intact (1,465 mentions in Mediarium, 419 in wings), and names, ports and
  environment variables remain visible in code.
- **Training-data exposure.** The repositories are public; a model may have
  seen an earlier version of a Dockerfile. Stars were capped at 400 to reduce
  this, and 6.6 has a code-based explanation, but exposure cannot be ruled out.
- **Sandbox effects.** The shim adds files and environment variables to every
  image (originals too). Candidates whose builds need plain HTTP or github.com
  downloads were excluded, which biased the set away from PHP.
- **Different build contexts.** Originals were built with their own
  `.dockerignore` and helper scripts; generated files with the model's.
- **Neutral prompt.** The models were not asked for security. A prompt that
  asks for it would probably score differently.
- **Snapshot in time.** CVE counts depend on the scan date and database
  (2026-11-17); base-image tags will resolve differently later.
- **One vendor, one harness.** Three Anthropic models through Claude Code.

## 9. Possible improvements and future work

- Three to five runs per pair to report variance.
- A second prompt condition that asks explicitly for a secure Dockerfile.
- A smoke test that starts each container and checks it stays up.
- Normalising CVEs by base image, or reporting only fixable CVEs in packages
  the Dockerfile itself installs.
- A random sample of Dockerfiles as well as the worst-scoring ones.
- Letting the agent build and iterate, as a separate condition.
- Running outside the sandbox to restore PHP and Java candidates.
